# 分阶段交付计划

> 2026-09-17 说明：本文保留生产化的长期门禁。当前仓库已经额外完成一条面向面试展示和小规模需求验证的本地产品 V1（成员 Web、Platform API、MCP Adapter、产品用例和 SQLite）。这不代表下列生产阶段被跳过；当前真实边界以 [V1 产品范围](../product/v1-scope.md)、[架构总览](./overview.md) 和根目录 [`SECURITY.md`](../../SECURITY.md) 为准。

每一阶段只有在退出标准全部通过后才结束。时间是规划，不是降低门禁的理由。

## 阶段 1：工程地基（第 1–2 周）

目标：先把协议、状态和边界变成可执行代码。

交付：

- Monorepo、统一 TypeScript/格式化/测试命令和 CI。
- `hsp-contracts`：版本字段、Envelope、稳定错误格式、核心消息 Schema、解析器和正反测试向量。
- `domain`：Handshake 状态、命令、转换结果、非法转换和乐观版本规则。
- 两个内存模拟 Endpoint 完成最短 HSP 流程；不接真实模型和数据库。
- 本目录中的架构、ADR、安全分类和 Runbook 索引。

退出标准：

- 全新环境执行 `pnpm install --frozen-lockfile` 和 `pnpm check` 成功。
- 每个合法转换、非法转换、终态重复消息、过期消息和重复 `message_id` 都有确定性测试。
- HSP 的有效/无效测试向量可由公开入口运行，未知消息类型和不支持版本默认拒绝。
- `domain` 与 `hsp-contracts` 无循环依赖，且无基础设施依赖。
- CI 阻止格式、类型、测试或构建失败的变更合并。
- 本阶段没有真实用户数据、供应商密钥或生产部署。

## 阶段 2：持久化纵切（第 3–4 周）

目标：跑通一个可恢复、可审计、幂等的双 Endpoint 会话。

当前 Idea 阶段先执行 3–5 个工作日的 SQLite 收缩验证，范围、停止条件和证据见
[phase-2-feasibility.md](./phase-2-feasibility.md)。验证通过只证明技术纵切成立，不自动授权建设下述生产能力。

交付：最小 `gateway-api`、PostgreSQL Repository、迁移、乐观锁、transition 日志、Transactional Outbox、Worker、身份签名校验、nonce/TTL、限流和超时任务。

退出标准：

- 两个模拟 Endpoint 通过 API 完成一条 Happy Path，并覆盖拒绝、超时、重放和并发冲突。
- 进程在事务提交或投递中断后重启，不丢状态且不重复产生业务副作用。
- 租户隔离集成测试证明 Community A 无法读写 Community B。
- 消息正文到期删除、用户删除和审计查询具有自动测试与可观测指标。
- 数据库迁移在与生产等价的副本上验证升级和回滚/前向修复路径。

## 阶段 3：封闭 MVP（第 5–8 周）

目标：单社区、单场景、两种模型完成真实用户闭环。

当前先从 [phase-3-experiment.md](./phase-3-experiment.md) 的合成资料实验开始；在隐私边界、
HSP 输出和人工可读性通过前，不接真实用户或生产模型密钥。

交付：Reference Agent、本地加密 Memory、Endpoint Policy、两个模型 Adapter、Intent、硬过滤与公开 Capsule 召回、六轮预算、用户介入、Member Web 最小页面。

退出标准：

- 原始 Memory、Embedding、私钥和供应商 API Key 不进入中心数据库、浏览器或日志。
- 每次披露可展示来源、用途、接收方和有效期，并可拒绝或撤销后续使用。
- 两个模型版本通过固定协议/安全/成本评估集；失败可切回无模型模拟器或上一版本。
- 单场景端到端成功率、P95 延迟、每次会话成本和人工介入率可观测，并达到发布时批准的 SLO。
- Endpoint 断网、模型限流和供应商不可用都有降级结果，而非无限重试。

## 阶段 4：试点运营（第 9–12 周）

目标：在邀请制社区中安全运营并能够处理故障和申诉。

交付：双重同意、反馈/举报/申诉、Operator Web、数据生命周期作业、监控告警、备份恢复、灰度与回滚、运营 Runbook。

退出标准：

- 安全、隐私和威胁模型评审无未接受的高风险项。
- 删除作业、密钥轮换、恢复演练、队列积压、供应商故障和疑似泄露 Runbook 完成演练并记录结果。
- Operator 权限最小化；正文访问需要临时审批且全部留痕。
- 10%→50%→100% 灰度可暂停、可回滚，重大指标回归能自动告警。
- 试点负责人签署 SLO、值班、用户支持和事件沟通责任。

## 阶段 5：白名单 Endpoint SDK 与生态接入（3–6 个月）

目标：在不开放任意接入的前提下，让受控第三方 Endpoint 能稳定实现 HSP。

交付：白名单 Endpoint SDK、协议测试向量与合规认证、兼容矩阵、接入沙箱、Endpoint 吊销机制、开发者文档，以及经过评审的更多场景/模型和多设备支持。

退出标准：

- 至少一个非 Reference Agent 的白名单 Endpoint 在沙箱和试点环境通过相同合规测试。
- SDK 覆盖签名、版本协商、幂等、超时、披露确认和稳定错误处理，不允许调用方绕过本地 Policy。
- Endpoint 可按单个密钥、版本或 Community 暂停/吊销，且不影响其他 Endpoint。
- 协议兼容矩阵、最短支持期、退役通知和回滚流程完成演练。
- 每个新接入方均完成数据分类、威胁评审、限流预算和负责人登记。

## 阶段 6：规模化与按证据拆服务（6–12 个月）

目标：依据真实容量、故障和组织数据扩展社区与部署边界，而不是预先微服务化。

交付：容量治理、灾备增强、按批准策略扩展社区；仅在满足下述门槛时拆分具有明确所有者的服务。

退出标准：

- 扩容或拆分决策具备至少 30 天的容量、SLO、成本和故障数据，并由对应 Owner 批准。
- 被拆模块拥有版本化 API、独立 SLO、值班、Dashboard、Runbook、容量测试和故障注入结果。
- 数据迁移、双写/切换、删除生命周期和回滚在与生产等价环境完成演练。
- 跨服务不使用共享表或分布式事务；Outbox/Inbox 幂等和端到端 Trace 验证通过。

阶段 5、6 的每个能力都需单独制定发布门禁；不得用“平台化”或“规模化”跳过数据分类、兼容测试或灰度。

## 服务拆分门槛

模块化单体是默认形态。只有至少出现一个硬触发条件，且拆分准备项全部完成，才提交服务拆分 ADR。

硬触发条件：

- 模块经查询/任务优化后仍需独立扩缩容才能满足已批准 SLO。
- 数据敏感等级、合规区域或密钥边界要求物理隔离。
- 该模块故障会反复拖垮核心会话，进程级隔离能显著缩小故障域。
- 有长期独立团队和明显不同的发布节奏，单体发布已成为可度量瓶颈。
- 必需运行时/技术栈无法在当前进程安全共存。

拆分准备项：明确 API 和版本策略、单一数据所有者、禁止跨库事务、Outbox/Inbox 幂等、端到端 Trace、容量测试、独立 SLO/值班/Runbook、数据迁移与回滚演练。仅仅“代码很多”或“未来可能扩容”不是拆分理由。
